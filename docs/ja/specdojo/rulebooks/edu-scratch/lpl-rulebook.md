# 活動別指導案 Rulebook

Lesson Plan Rulebook

Scratch の活動ごとに作る指導案の置き方と、学習目標、制作、評価を矛盾なく記録する方法を定める。活動固有の題材、時間、使用機能、授業運営は、各活動の根拠と学習者・端末の状況に基づいて決める。

## 1. 全体方針

- 対象は `courses/<course-id>/lessons/<nnn>-<activity-id>/lesson-plan.md` に置く、1 回の活動を扱う Markdown 指導案とする。
- 指導案は、授業で何を目指し、何を作り、どの順で確かめ、どの到達を見取るかを、授業者が照合できる形で記録する。
- ねらい、使用機能、完成形、学習活動、評価・見取りは、同じ活動で扱う内容に対応させる。完成形だけ、または使用機能だけを孤立して列挙しない。
- コース内での前後関係はコース計画を根拠にするが、コース計画から参照される旧設計を、確認せずに指導案の根拠へ加えない。
- 具体的な題材、分数、段階数、保存形式、共有方法、Scratch のブロック名は活動ごとに決める。1 件の指導案にある値を全活動の規則にはしない。

## 2. 位置づけと用語

活動別指導案は、コース計画が示す学習の積み上がりを、1 回の授業で実行できる学習活動へ具体化する文書である。投影資料、開始用プロジェクト、完成見本を作る場合は、指導案で定めたねらい、完成形、時間配分をそれらの判断根拠にする。

| 用語       | この rulebook での意味                                             | 指導案で確認すること                               |
| ---------- | ------------------------------------------------------------------ | -------------------------------------------------- |
| 最低完成形 | 時間不足時にも優先して到達させる、作品の最小の動作・説明可能な状態 | ねらいの最低限と対応し、授業中に確かめられる       |
| 標準完成形 | その活動で通常目指す、使用機能と作品の振る舞いを満たす状態         | 使用機能、学習活動、評価・見取りと対応する         |
| 発展形     | 標準完成形を基に、学習者が選んで改造・表現・説明を深める状態       | 未到達の学習者を待たせず、追いつく時間も確保できる |
| 見取り     | 学習者の作品、操作、説明、振り返りから到達を確認すること           | 各完成形で見る行動または作品の状態が分かる         |

## 3. ファイル命名・ID規則

- 指導案の正本は `courses/<course-id>/lessons/<nnn>-<activity-id>/lesson-plan.md` に 1 つだけ置く。
- `<nnn>` は活動順を表す 3 桁の連番、`<activity-id>` は活動を区別する小文字ハイフン区切りの名前とし、同じコース内で重複させない。
- ファイル名は `lesson-plan.md` とする。完成見本、開始用プロジェクト、投影資料などは、それぞれの成果物の規約に従って管理し、指導案の複製として置かない。
- カタログと Schedule で管理する指導案は、ファイル先頭の YAML frontmatter に成果物固有の `specdojo:` を持つ。kata の ID や `type: template` / `sample` を教材へコピーしない。
- 指導案・コース計画・教材スライドはプロダクト文書であり、[[specdojo:id-and-file-naming-standard|ドキュメントIDおよびファイル命名標準]] に従って、`id` はカタログの対象行の `local_id` と一致する修飾なし ID とする。同じ SpecDojo Unit 内で一意にし、配置パスと 1 対 1 に対応させる。ファイル名や活動ディレクトリ名から別の ID を作らない。
- 例えば `project_id: prj-0001`、`local_id: lpl-balloon-game` の教材自身の正規 ID は `lpl-balloon-game`。CLI の成果物指定やカタログ内部の識別に使う `<project-id>:<local-id>` と、教材の `specdojo.id` を区別する。プロジェクト文書の `prj-0001:`、型の文書の `edu-scratch:` はそれぞれの文書に残す。

## 4. 推奨 Frontmatter 項目

### 4.1. 教材固有のメタ情報

[[specdojo:document-metadata-standard|ドキュメントメタ情報標準]] と、導入済み SpecDojo の `docs/specdojo/schemas/v1/common-frontmatter.schema.yaml` / `deliverable-frontmatter.schema.yaml` を根拠とする。以下の必須項目は `specdojo:` 配下に置く。

| 項目       | 採用値・根拠                                                                                                                                 |
| ---------- | -------------------------------------------------------------------------------------------------------------------------------------------- |
| `id`       | 第3章の修飾なし `local_id`。共通 schema が許容する小文字・数字・ハイフンを使う。                                                             |
| `type`     | `project`。既存の成果物 schema の列挙値を使う。これは ID の namespace とは別の概念であり、独自の `product`・`lesson-plan` 型は追加しない。   |
| `status`   | 作成・移行時は `draft`。文書成熟度であり、Schedule の実行状態や授業実施済みを表さない。検証成功だけで `ready` にせず、人間が昇格を判断する。 |
| `rulebook` | `edu-scratch:lpl-rulebook`。実在するこの rulebook の ID を使い、カタログの宣言とも一致させる。                                               |

- 題名は H1、対象、所要時間、テーマなどの授業概要は本文に記載する。`specdojo:` 配下へ `title`、`duration`、`course_id`、`project_id`、`depends_on` など未定義の項目を増やさない。
- `based_on`、`part_of`、`supersedes` は schema にある任意の ID 配列であり、必要な場合だけ使う。`based_on` は確認済みの根拠だけとし、カタログの `depends_on` の推移閉包に含まれる先行成果物に限る。教材間の参照は修飾なしの正規 ID（例：`cpl-scratch-basic`）を使う。コース計画への依存が未登録なら、本文の位置づけに根拠を記し、メタ情報への追加はカタログ整備後に行う。
- メタ情報を追加するために授業本文、活動順序、時間、配置パスや Schedule を変更しない。

### 4.2. kata と教材用記入欄

- [[edu-scratch:lpl-template|指導案 template]] 自身の `id`・`type`・`status` と、先頭の YAML コメントにある教材用記入欄を区別する。教材化時は記入欄の値を確定し、kata 自身の `specdojo:` 全体を教材用に置き換える。記入欄のコメントと作成者向け案内を除き、教材の frontmatter は残す。
- [[edu-scratch:lpl-sample|指導案 sample]] のメタ情報は完成例を所有する kata のもの。コメントに示す仮想の教材 ID も、そのまま実在の教材へコピーしない。
- 標準の `frontmatter_template` は、導入済み成果物 schema の許可項目には含まれないため、ここでは追加せず YAML コメントで出力形を示す。自動展開には依存せず、置換した教材の frontmatter を通常の成果物 schema で検証する。

### 4.3. コース計画の扱い

コース計画もプロダクト文書であり、同じ成果物 schema を使って、`type: project`、作成・移行時の `status: draft`、登録するカタログの `local_id` と一致する修飾なし ID（例：`cpl-scratch-basic`）を採用できる。現時点ではコース計画用の rulebook は未整備なので、`rulebook: none` とする。これは共通 schema が許可する値であり、指導案やカタログ用の無関係な rulebook を割り当てない。

コース計画のカタログとの照合・教材本体への反映は後続作業で行う。この指導案 kata の対象をコース計画本文へ拡張したり、新しいコース計画 kata を作ったりしない。カタログ側の `rulebook` の未整備表現（`undecided` 等）と、成果物 frontmatter の `none` は別の schema の値であり、混用しない。

## 5. 本文要件

次の順序と役割を本文の骨組みとする。template は、この表で示す章と表の役割を保ち、記入欄の表現を正本にする。

| 章・区分                 | 必須 | 目的と記載条件                                                                                                                           | 整合の確認                                                                                         |
| ------------------------ | ---- | ---------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------- |
| 授業の概要               | 必須 | 対象、所要時間、テーマ、授業のねらい、使用する主な機能を記す。ねらいは作品で行うことと結び付ける。                                       | 使用機能が標準完成形と学習活動に現れる。                                                           |
| 授業の位置づけ           | 必須 | 前の活動から何を引き継ぎ、次の活動へ何をつなぐかを、確認したコース計画に基づいて記す。                                                   | 前後の活動・概念を推測で追加しない。                                                               |
| 完成する作品             | 必須 | 作品全体の振る舞いと、最低・標準・発展の完成形を分けて記す。各段階は観察または説明で確かめられるようにする。                             | 最低完成形は時間不足時に残す線、標準完成形はねらい・使用機能の中心、発展形は任意の工夫に対応する。 |
| 事前準備                 | 必須 | 教師用の完成見本、開始用プロジェクト、素材・端末など、授業開始前に必要なものと確認事項を記す。                                           | 初期化、終了、再開に必要な状態と、制作で学習者に残す作業を対応させる。                             |
| 授業の流れ               | 必須 | 導入、制作、発展、まとめなどの区間ごとに、時間、学習内容・活動、指導上の留意点を表などで対応させる。                                     | 区間の合計時間が授業全体の所要時間と一致する。                                                     |
| 進め方と進度差への対応   | 必須 | 教師と操作してから改造する進め方を採る活動では、提示、学習者の操作、動作確認、改造の順と、先にできた学習者・遅れた学習者への対応を記す。 | 全員待ち、特定の段階数、途中プロジェクトの配布を一律の前提にしない。                               |
| 評価・見取り             | 必須 | 最低・標準・発展の各完成形に対応する、作品の状態、操作、説明、振り返りなどの観点を記す。                                                 | 評価が、完成形と授業中の学習活動の両方を確認できる。                                               |
| 声かけとつまずきへの対応 | 必須 | 起こり得るつまずきを、活動の使用機能や作品の動作に結び付け、確認する順序または次の試行を記す。                                           | 未確認のブロック名、値、端末挙動を確定事実として書かない。                                         |
| まとめと次回へのつなぎ   | 必須 | 本時で振り返る考え方、保存・共有を扱うかどうか、次回へつなぐ内容を記す。                                                                 | 保存形式、共有相手・方法、次回接続は活動ごとの判断として具体化する。                               |

## 6. 記述ガイド

### 6.1. 対応関係の書き方

- ねらいごとに、どの使用機能または作品の振る舞いで扱い、どの完成形・学習活動・見取りで確かめるかを追えるように書く。
- 使用機能は、単なる機能名の一覧にせず、作品内での役割を添える。手本にない概念を、一般的な Scratch の知識だけを理由に追加しない。
- 最低完成形には、時間が不足しても残す動作と、その到達を確かめる行動を記す。標準完成形に届かない学習者が発展時間で何を優先するかも、活動に応じて示す。
- 発展形は、数値、表示、動き、遊び方、表現など、標準完成形を壊さずに試せる活動固有の選択肢とする。全活動に同じ改造内容を求めない。

### 6.2. 時間と授業運営の書き方

- 授業の流れは、各区間の時間を明記し、合計が概要の所要時間と一致するようにする。時間が変更されたら、区間と完成形の到達線も見直す。
- 時間不足時は、削ってよい改造・共有・発展と、残す最低完成形を区別して記す。授業時間を一律に 45 分、または導入・基本制作・発展・まとめの固定配分にしない。
- 教師の画面に合わせる活動では、各制作区間で何を操作・動作確認・改造するかを分けて書く。進め方が異なる活動では、その活動に合う支援方法を記す。
- 先にできた学習者には、待機ではなく活動に結び付く改造・説明・確認を用意する。遅れた学習者には、最低完成形へ戻る支援を、完成見本や画面共有など実際に使う手段に合わせて記す。

### 6.3. 準備、状態、保存・共有の書き方

- 完成見本は、授業の開始から終了までを動かして確認し、初期化、終了条件、再開時に戻す状態を、活動で必要な範囲だけ記す。
- 開始用プロジェクトを使う場合は、あらかじめ入れるものと、学習者が作る機会として残すものを分ける。途中段階のプロジェクトを配るかどうかは、活動ごとに判断して明記する。
- 端末、素材、拡張機能、カメラなどの前提は、授業前に確認する内容と対応させる。実機で未確認の操作名や挙動は、確認事項として扱う。
- 保存・共有を行う場合は、保存形式または保存先、見せる相手・方法、実施する時間を記す。保存や共有を扱わない活動では、行わない理由または授業上の扱いを明確にする。

### 6.4. 評価とつまずきの書き方

- 評価・見取りは、「できた」とだけ書かず、旗や入力から作品を動かす、結果を説明する、変更を比較するなど、見取る行動を具体化する。
- つまずきは、初期化不足、開始・終了の制御、表示と動作のずれ、使用機能の役割の混同など、活動で実際に確認する点に結び付ける。
- 声かけは答えを与えるだけでなく、まず何を動かして見るか、どの変更を 1 つに絞るかを促す。未確認の原因や解決手順を万能なものとして断定しない。
- まとめでは、作品の完成だけでなく、試して直したことや工夫したことを振り返る。次回接続は、コース計画で確認した範囲にとどめる。

## 7. 禁止事項

- 45 分、特定の制作段階数、全員が終わるまで待つ進行、途中段階のプロジェクトを配らないことを、すべての活動に共通する規則として書かない。
- 特定の題材、スプライト、得点、数値、メッセージ名、完成条件を、根拠なく共通の完成形や評価基準にしない。
- ねらい、使用機能、完成形、学習活動、見取りのいずれかを対応付けずに列挙しない。また、区間時間の合計と授業時間が矛盾したままにしない。
- 初期化、終了、再開に必要な状態を準備から切り離したり、保存・共有を活動の判断なしに必須または不要と断定したりしない。
- 手本にない概念、未確認のリンク先、端末固有の操作・挙動を、確認済みの事実として書かない。
- この rulebook に完成例全文、題材別のブロック構成、作成手順を置かない。完成例は sample、内容を組み立てる手順は recipe、記入欄の正本は template で扱う。
